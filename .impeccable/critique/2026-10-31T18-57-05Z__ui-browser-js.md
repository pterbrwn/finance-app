# Ledger UI/UX critique — implemented round

Target: `ui/browser.js`, current working tree and rendered dashboard. Mode: Operate. Two independent assessments: design and technical/browser. Empty and synthetic sample data only.

## Design specificity
The quiet green palette and clear distinctions among actual balances, plans, and hypothetical scenarios suit household finance. The repeated card scaffolding and slogan remain generic. Ledger's most valuable product character is a safe, understandable money task; the interaction gaps now undermine that character.

Deterministic scan: `impeccable detect --json ui/browser.js` returned `[]` (zero findings). It did not catch the serious rendered contrast failure, draft loss, or unreachable selection review. No user-visible detector overlay was demonstrated; the documented cross-port script conflicts with the app's `script-src 'self'` CSP.

## Overall impression
The initial Overview and rough payment preview improve first use, and responsive pages avoid document overflow. The round is not ready to treat as finished because two promised safety controls fail in the browser.

## What works
- Empty Overview leads to an account action and separates sample preview from real records (`ui/browser.js:250`).
- Actual balance, plan, and hypothetical scenario language is generally explicit (`ui/browser.js:106`, `ui/browser.js:234`).
- The rough scenario preview gives principal and interest after core inputs and names excluded costs. Synthetic $250,000 purchase and $50,000 down produced $1,264.14 per month (`ui/browser.js:228`).
- Browser renders at 320, 390, 768, and 1440px showed no document-level horizontal overflow on Overview, Transactions, Budgets, and Home.

## Priority issues
1. **P1 — Declining discard can still lose a draft.** In a fresh browser, dismissing the native prompt after editing a scenario or manual account still closes the dialog. An edited property closes on Escape without a prompt. Extra per-dialog `cancel` handlers override the shared guard, and property does not use it (`ui/dialogs.mjs:11`, `ui/browser.js:228`, `ui/browser.js:239`, `ui/browser.js:299`). Consolidate close behavior in the shared helper, with one cancel path and explicit clean state after a successful save. Suggested command: `$impeccable harden`.
2. **P1 — Bulk selection review is unreachable.** The selected bar renders only a count, category picker, and immediate Categorize action. The `#review-selected` handler exists, but the button does not render; cross-page records cannot be inspected before write (`ui/browser.js:152`, `ui/browser.js:294`). Render the review and clear controls, and require review before applying a cross-page change. Suggested command: `$impeccable harden`.
3. **P1 — Financial text contrast still fails.** Axe found one serious color-contrast rule affecting 10 nodes on sample Overview and 22 date cells on sample Transactions. The inline transaction date color `#8b968b` on white is about 3.07:1 at 10px; budget small labels also fail (`ui/browser.js:126`, `ui/styles.css:1`). Remove the inline pale date color, raise functional label size, and recheck rendered states. Suggested command: `$impeccable typeset`.
4. **P2 — Mobile task hierarchy is still crowded.** At 390px Transactions puts search, six filters, Clear, Import, Export, and New category ahead of the list. Empty Budgets presents a horizontally clipped ten-row household matrix with about 30 edit links and no first-plan action (`ui/browser.js:152`, `ui/browser.js:156`, `ui/styles.css:28`). Put routine review first; group secondary filters/actions and provide an empty-plan path. Suggested commands: `$impeccable layout`, `$impeccable adapt`.
5. **P2 — Scenario labels contradict the early estimate.** The opening section still exposes roughly nine decisions, and a generated label says “Purchase price (USD / month where applicable) · Enter 0 if none,” even though purchase price is one-time and must be positive (`ui/browser.js:226`). Use field-specific units and guidance; make the rough result easy to see before advanced input. Suggested commands: `$impeccable clarify`, `$impeccable onboard`.

## Persona red flags and cognitive load
- Nontechnical partner: price and payment units can mislead; a declined discard prompt can still erase work.
- Power user: cross-page selection count is visible, but the promised selected-record review is absent before bulk change.
- Mobile user: routine transaction review is pushed below a long control block, and empty Budgets begins with a dense matrix.
- Keyboard/screen reader user: focused mobile selector has a visible 3px outline; dialog cancel behavior is inconsistent. Actual screen-reader use remains unverified.

The first-use journey starts clearly on Overview and improves with a rough scenario payment. Confidence drops at the long form and sharply at draft exit and bulk categorization. The major failed cognitive-load checks are first action clarity on Transactions/Budgets and too many simultaneous scenario choices.

## Minor observations and questions
Axe reported zero violations on empty Overview and sample Budgets/Home; the severe contrast is concentrated in transaction dates and small labels. There was no observed document overflow. What would the first transaction task look like if only search and results were initially visible? Which scenario fields genuinely belong before the first estimate?
